0. 要解决的问题

给定一段带请求边界的 KVCache block 访问 trace，和一组候选缓存容量（如 1GB / 2GB / 4GB / 无限），问：每个容量下的 prefix 命中率各是多少？用于回答“缓存扩容到多大收益如何”这类容量规划问题。

朴素做法为什么不行
为 K 个容量各维护一套真实 LRU，回放 K 遍（或一遍内更新 K 套链表）——时间和内存都是 K 倍，容量点一多就不可行。

LiteHit 的目标：只维护一套状态、回放一遍，精确（非近似）得到所有容量的结果。第一阶段约束：full attention、等 charge block、精确 LRU、容量集合开始时固定，支持 0 / 有限 / 无限容量。

1. 理论基础：LRU 栈包含性质（Stack Inclusion）

这是整个算法的支点：

栈包含性质
容量为 C 的 LRU 缓存内容，恰好是“全局按最近访问时间排序”这条序列的前 C 个元素。小容量缓存永远是大容量缓存的子集。

例：全局最近访问顺序为 MRU → [X, A, Y, B] → LRU：

X深度 1
A深度 2
Y深度 3
B深度 4
容量 1 的缓存 = {X}
容量 2 的缓存 = {X, A}
容量 3 的缓存 = {X, A, Y}
容量 4 的缓存 = {X, A, Y, B}

所以 K 套 LRU 缓存其实是同一条全局顺序的 K 个前缀——只要维护这一条全局顺序，就能同时回答所有容量。

推论：最小命中容量
某次访问 block B 时，若 B 在全局 LRU 序中排第 p 位，则它在容量 C ≥ p 时命中、C < p 时 miss。p 就是这次访问的 required_capacity。

2. Reuse Distance 与 Fenwick 树

2.1 reuse distance

block 在全局 LRU 序中的深度，等价于：

reuse distance d = 该 block 上次访问之后、这次访问之前，
                   出现过的【不同】block 数
required_capacity = d + 1

第一次出现的 block 是 cold miss，没有有限的 required_capacity——无限容量也救不了 cold miss。

2.2 Fenwick 树怎么算 d

直接数“区间内不同 block 数”很贵。经典技巧（Bennett–Kruskal / Mattson 算法一脉）是：

  • 给每次访问分配递增的位置序号；每个 block 只保留最新位置（last_positions_）；
  • Fenwick 逻辑数组：marker[pos] = 1 当且仅当 pos 是某个 block 的最新位置，否则为 0。

于是“区间 (prev, now] 内仍为 1 的位置数”就等于“比当前 block 更新的不同 block 数”：

// lite_hit.cc — ReuseDistance
d = fenwick.PrefixSum(size) - fenwick.PrefixSum(prev);

block 更新位置时，把旧位置的 1 清掉、新位置标 1，保证“每个活跃 block 恰好贡献一个 1”。单次操作 O(log n)。

Fenwick 不是缓存
它不是一套 cache，也不是额外的 LRU 链，只是全局 LRU 顺序的 order-statistics 视图。

DynamicFenwickTree 是可追加的变体：AppendZero() 在末尾加一个逻辑 0，并用当前前缀和给新树节点播种，使后续 Add 保持所有祖先节点一致——避免预分配整个 trace 长度的数组。

3. 从独立命中到 Prefix 命中

full-attention 的语义是前缀命中：请求 [A, B, C, D] 中如果 C miss，即使 D 独立看是 hit，也不能贡献命中（推理必须从第一个 miss 处开始重算）。

请求 block：   [A,   B,   C,    D  ]
独立判断：      hit  hit  miss  hit
本条请求结果：  hit_count = 2       ← D 不能越过 C

设请求内各 block 的最小命中容量为 [r1, r2, ..., rm]，第 j 个 block 贡献 prefix hit 需要容量满足前面所有 block：

prefix_required[j] = max(r1, r2, ..., rj)     ← running max

实现见 EvaluateRequestPrefix（lite_hit.cc:108）：逐 block 维护 running max；遇到首个 cold block 直接 break——cold 对任何容量（含无限）都截断 prefix。

关键点：miss 截断计数，但不停止状态更新
首个 miss 只截断本条请求的 hit_count。所有完整 block 仍按序进入/刷新全局 LRU（否则下一条请求看到的缓存状态就错了）。这正是“评估”和“提交”分离的原因（见第 5 节）。

4. 容量维度差分：一次访问不逐容量记账

有了门槛 prefix_required[j] = R，意味着该 block 对所有 C ≥ R 的容量各贡献一次命中。逐容量 +1 又回到 O(K)。LiteHit 用差分数组 hit_deltas_：

  • 初始化时把有限容量排序去重，无限容量排在最后；
  • 每个门槛 R 只在“第一个 ≥ R 的容量”处 +1，二分查找 O(log K)（FirstCapacityAtLeast）；
  • 输出时沿容量从小到大做一次前缀和（ResolveHitDeltas），再映射回用户原始输入顺序（含重复容量）。

例：容量 [1, 2, 4, ∞]，某请求门槛为 [2, 4, 4]：

容量：       [1,  2,  4,  ∞]
gain（差分）：[0,  1,  2,  0]   ← R=2 落在容量2；两个 R=4 落在容量4
前缀和 →
hit_count：  [0,  1,  3,  3]

5. 两阶段处理：快照评估 + 批量提交

ProcessRequest 不逐 block 交替“查询 + 更新”，而是分两阶段：

阶段一：只读快照评估（EvaluateRequestPrefix）

基于请求到达前的 LRU 快照，为请求中每个不同 key 查一次深度；重复 key 复用同一快照条目。

为什么快照评估是合法的
对任意容量，首个 miss 之前全是 hit，而 hit 只改变顺序、不改变缓存成员集合。所以“首个 miss 的位置”只取决于请求前的快照，与请求内前面的 hit 如何刷新顺序无关。

阶段二：批量提交（CommitRequest）

按每个不同 key 的最后一次出现顺序提交：先把这些 key 的旧 marker 全部清 0，再按请求内最后出现的先后顺序追加新位置（越晚出现越靠近 MRU）。这与逐 block 顺序访问的最终状态严格等价：

旧 LRU: [X, A, B, C]，请求 [A, B, A]

顺序访问：A→[A,X,B,C]  B→[B,A,X,C]  A→[A,B,X,C]
批量提交：A 最后出现在位置 3、B 在位置 2
          → 同样得到 [A, B, X, C]  ✓

6. 内存控制：剪枝与压缩

Online 长流场景有两个内存问题，各有一个机制应对：

机制解决的问题做法
PruneToTrackedCapacity
lite_hit.cc:181		 unique key 无限增长 无“无限容量”配置时，掉出最大有限容量之外的 key 对所有查询容量必然 miss，等价 cold——直接从 Fenwick 和 last_positions_ 删除。用单调队列 position_order_ 找最老活跃 marker（惰性跳过失效条目）。效果：U ≤ 最大有限容量。
MaybeCompactPositions
lite_hit.cc:201		 位置序号只增不减，Fenwick 数组随历史访问数膨胀（大量 0 洞） 当活跃位置不足超额部分一半时（slack 阈值 4096），把所有活跃 key 按原相对顺序重编号，重建紧凑 Fenwick。摊还后空间由当前活跃状态而非历史总访问数主导。

只有配置了无限容量时，才必须保留全部历史 unique key（用于区分 cold / reuse）。

7. Token 命中率换算：两个不能混淆的“大小”

量单位用途
block_size_tokenstoken / block把 prefix hit block 数换算成命中 token 数
block_charge_bytesbyte / block把字节容量换算成 block 容量：floor(capacity_bytes / block_charge_bytes)，在 Online/Offline 适配层完成，LiteHit 核心只见 block 数
hit_rate = hit_count × block_size_tokens / input_token_len
  • 尾部不足一个 block 的 token 不进 LRU，但留在分母：50 token、block=16、全命中 → 48/50 = 96%，不是 100%。
  • 累计命中率必须先累加整数分子分母再相除，不能对每条请求的命中率取算术平均（请求长短不同）。

9. 复杂度与整体流程

设 N = 总 block 访问数，K = 容量数，U = 活跃 unique block 数（有限容量时 ≤ 最大容量），Q = 请求数：

  • 每次 block 访问：Fenwick 查询/更新 O(log U) + 容量二分 O(log K)；
  • 每条请求输出：O(K)（要输出 K 个结果，不可避免）；
  • 持久状态：只有 Fenwick、last_positions_、容量映射、累计计数——不保留原始 trace、不保留逐访问 reuse distance、不维护 K 套 LRU 链。
多个容量的 LRU cache
↓ LRU 栈包含性质
一条全局最近访问顺序（Fenwick + last_positions）
↓ reuse distance d → required_capacity = d + 1
每次访问的最小命中容量
↓ 请求内 prefix max + 容量差分
所有目标容量的 prefix hit_count
↓ × block_size_tokens ÷ input_token_len
每条请求 & 累计 token 命中率
正确性验证
用朴素多容量 LRU 做 oracle 对拍（test/lite_hit_test.cc）：逐请求 hit_count 一致、请求后 LRU 状态一致、Offline 批量与 Online 逐请求一致；覆盖容量 0、重复容量、无限容量、cold miss、请求内重复 key、不完整尾部 token。
